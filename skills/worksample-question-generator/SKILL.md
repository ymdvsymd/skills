# ワークサンプル深掘り質問ジェネレーター

応募者が事前提出したワークサンプル／技術課題の回答を批判的に読み、面接当日に深掘りすべき質問・示唆を、課題の問いごとに整理して出力する。

## なぜこのスキルが必要か

応募者の事前回答は「時間をかけて整えた成果物」であり、額面通り受け取るだけでは候補者の思考の深さ・スタンス・実現可能性の理解度が見えない。面接の限られた時間（60分など）でそれを引き出すには、回答の中の **論理の飛躍・前提の弱さ・実現プロセスの抽象度・代替案の不在・スタンスの曖昧さ** を狙い撃ちした質問を準備しておく必要がある。

このスキルは、回答を批判的に読み解き、面接官が「ここを深掘りしたい」と感じるであろうポイントを発見して、質問の素案として整理する。**答えを与えるのではなく、面接官が候補者の口から聞きたい「思考プロセス」「スタンス」「具体策」を引き出せる問いかけ**を生成する。

## ワークフロー

1. **入力ファイルを特定**
   - ユーザーから明示的に渡された課題ファイルと回答ファイル（複数可）を読む
   - 渡されたパスが曖昧なら確認する。1つしか渡されていない、課題か回答か区別できない場合は確認する
   - 回答が PDF（ワイヤーフレームなど）と Markdown 両方など複数に分かれている場合は全て読み込む

2. **入力ファイルを丁寧に読む**
   - 課題側: 何を問うているか、いくつの問いがあるか、シナリオの前提（市場・チーム構成・既存システム）を把握する
   - 回答側: 候補者の主張・仮定・優先順位・スコープ判断・スキーマ・UI判断を把握する
   - ワイヤーフレームのような視覚情報がある場合は、その意図と画面選択の根拠を把握する

3. **質問観点チェックリストを順に当てる**（後述）
   - 回答全体を読みながら、各観点で「深掘りすべきポイント」を発見する
   - 1つの問いに対して、深掘りポイントは複数あって構わない

4. **問いごとに質問を整理して出力**
   - 課題内の問い番号（Q1, Q2, ...）に対応させる
   - 各問いごとに、冒頭の評価（1行）→ 深掘り質問群 → 必要に応じて示唆・フレームワーク・代替案の例
   - **出力先は入力ファイルと同じフォルダ**に `ワークサンプル質問.md` という名前で保存する（既存ファイルがあれば確認するか上書きする）

5. **出力後にユーザーに簡潔に伝える**
   - 保存したファイルのフルパスを示す
   - 全体で何個の質問を生成したかを1〜2文で伝える

## 入力

ユーザーから以下を受け取る。明示されない場合は確認する:

- **課題ファイル**: ワークサンプル／技術課題の問題文（PDF / MD / テキスト）
- **回答ファイル**: 応募者が提出した回答（PDF / MD / テキスト）。複数ファイル可（ワイヤーフレーム PDF が別添など）
- **（任意）ポジション情報**: 「EM/TL」「フロントエンドエンジニア」「PM」など。課題側に書かれていればそちらを優先

候補者名はファイル名やフォルダ名、回答ファイル内のフッター・タイトルなどから推定する。推定不能なら無理に書かない（「候補者」「応募者」などの汎用語で代替）。

## 出力フォーマット

入力ファイルと同じフォルダに `ワークサンプル質問.md` を生成する。中身は以下のテンプレート:

```markdown
# ワークサンプル質問 — <候補者名 or 課題名>

> 課題: <課題ファイルの簡潔な要約 / タイトル>
> 回答: <参照した回答ファイル名>

---

## Q1: <課題の問いの簡潔な見出し>

<冒頭の全体評価。1〜2文。例: 「優先順位の仮定は一定理解ができる」「それぞれの問いに対する自身のスタンスを明確にしてほしい」>

- **<深掘りポイントのラベル>**: <質問本文。1〜3文>
- **<深掘りポイントのラベル>**: <質問本文>
...

### 示唆 / 思考フレーム（必要に応じて）

<答えを与えずに、候補者が考えるべきフレームワーク・代替アクションの例を列挙。これは面接の場で議論を広げる材料>

---

## Q2: ...

（同様）
```

### 出力フォーマットの設計意図

- **Q番号は課題に合わせる**: 課題が4つの問いを持つなら Q1〜Q4 を生成する
- **冒頭の評価 + 深掘り質問**: 評価で候補者の回答を受け止めた上で、批判的に掘る
- **示唆セクションは任意**: 答えを与えない（誘導しない）が、面接官が議論を広げる材料として、フレームや代替案の例を箇条書きで添える
- **質問本文は口語的でよい**: 「これだけ見ると解決不可能な問題に見える」「最も優先順位高いactionがこれなのか?」のような自然な書き口でOK

## 質問を作る観点（チェックリスト）

回答を読みながら、以下の8つの観点を順に当てて深掘りポイントを発見する。**全観点を毎回当てる必要はない**が、ピンと来る箇所を逃さないようにする。

### 1. スタンスが明確か

- 「〜のため」「〜が望ましい」と書いているが、自分が意思決定者だったら何をやるかが書かれていない
- 「〜という方向で進めて良いでしょうか?」のような確認形のまま、自分のスタンスが薄い
- 「予想される課題」を列挙しているだけで、どう向き合うかが書かれていない

→ 質問例: 「実際に意思決定する立場にいるとして、どういうプロセス／ロジックで判断するか」

### 2. 論理の飛躍 / 整合性

- 仮定 → 結論の間に論理が省略されている
- 優先順位や仮説と、実際のスコープ（MVP, ロードマップなど）の紐付きが薄い
- 「最も優先順位高い」と書いているが、それに紐づくアクションが少ない／弱い

→ 質問例: 「優先順位の整理と、実際のMVPのscopeがあまり紐づいていないように見える。一番優先順位高いのにこれだけでいいの?」

### 3. 「解決不可能」で止まっていないか

- 「予想される課題」「現実的な課題」を列挙して終わっていて、どう乗り越えるかが書かれていない
- 業界の他社・競合がどう解決しているかへの言及がない

→ 質問例: 「これだけ見ると解決不可能な問題に見える。競合とかってどういうふうに対応してるのか」

### 4. 実現プロセスは具体的か

- 「人力で構築する」「AIで自動生成する」など抽象度の高い記述で止まっている
- 実際の運用プロセス・人数・期間・コスト・ガバナンスの想定がない

→ 質問例: 「実際に人間が辞書を構築するとしたらどういうプロセスになるのか?」

### 5. 代替案の検討は十分か

- 提案された施策以外に、課題を解決する別アプローチを検討した形跡がない
- 「これが最善」と言える比較根拠がない

→ 質問例: 「他に仮説／Actionってないか。最も優先順位高いactionがこれなのか?」
→ **具体的な代替案を示唆として箇条書きで添える**（答えではなく、候補者が考慮すべきだった例として）

### 6. ユーザー体験のフロー全体を捉えているか

- 単発の機能で終わっていて、ユーザーの一連のジャーニー（入力 → 判断 → 確認）で整理されていない
- フロー全体での課題分解がない

→ 質問例: 「ユーザーの一連の体験を洗い出して、フロー別に整理してみる」
→ フローの例を示唆として添える（「商品情報を入力 → 価格を決定 → 出品後のステータス確認」など）

### 7. データスキーマ / 設計の判断根拠

- テーブル分割・追加・省略の判断根拠が明確か
- 抜けている考慮点（NULL設計・インデックス戦略・セキュリティ・スケーラビリティ）はないか
- 「省略した」と書かれている部分について、なぜ省略したかの基準は明確か（時間の都合か、本質的に不要と判断したか）

→ 質問例: 「この設計を選んだ判断基準は何か。省略した部分は本当に省略して良いと判断したのか、時間の都合か」

### 8. ワイヤーフレーム / UI の根拠

- 画面選択の根拠が、MVP のスコープと整合しているか
- UI 要素の配置・遷移の意図は説明できるか
- 他にも候補となる画面があったはずなのに、なぜこれを選んだか

→ 質問例: 「この画面を選んだ理由を、MVPの優先順位と照らして説明できるか」

## 良い質問と悪い質問

### 良い質問
- 候補者の口から「思考プロセス」「スタンス」「具体策」を引き出せる
- Yes/No で終わらない、オープンクエスチョン
- 候補者が事前に準備していなかったが、実務では当然考えるべきこと
- 「具体例」や「フレームワーク」を示唆として並べることで、面接の場で議論が広がる

### 悪い質問（避ける）
- 答えが既に回答に書かれていることをそのまま聞き直す（読めば分かることを聞かない）
- 賞賛だけで深掘りしない（「素晴らしいですね」「良い回答です」だけ）
- 詰問調・萎縮させる書き方（批判的でも、対等な議論を促す姿勢で書く）
- 自分の正解を押し付ける誘導質問（示唆は「例えば〜」の例示で留め、答えを述べない）
- 1つの質問に複数の問いを詰め込みすぎる（1観点1質問が基本）

## 出力のトーン

- 簡潔で、面接官が手元で読みながら使える長さ
- カジュアルな書き口でも構わない（「優先順位の仮定は一定理解ができる」「これだけ見ると解決不可能な問題に見える」のような口語表現）
- 過度に丁寧でも詰問調でもない、対等な議論を促す書き方
- 候補者名を呼ぶ場合は「さん」付け（例: 「実際に〇〇さんが意思決定する立場にいるとして」）

## 参考: 期待される出力スタイル

以下は EM/TL ポジションのワークサンプル課題に対する Q1, Q2 部分の出力サンプル。**このスタイル・密度・批判性を目安とする**。

```
Q1:

それぞれの問いに対する自身のスタンスを明確にしてほしい。

実際に〇〇さんが意思決定する立場にいるとして
競合のProductを分析した上で現在自社が実装している機能とのギャップを特定した場合どういうプロセス／ロジックでそれらのやるやらを判断するか

真贋判定の精度のところで予想される課題いくつか挙げてるが、これだけ見ると解決不可能な問題に見える。競合とかってどういうふうに対応してるのか

シノニム辞書:
実際に人間が辞書を構築するとしたらどういうプロセスになるのか?
```

```
Q2:

優先順位の仮定は一定理解ができる
ECサイト(特にマーケットプレイス型)の購買行動は、「出品 → 検索ヒット → 購入」というファネル(漏斗)構造で上流が細いと、下流をいくら改善しても全体のスループットは増えない的な。

ただ、この優先順位の整理と、実際のMVPのscopeがあまり紐づいていないように見える。

まず、出品体験の改善につながる具体施策ってどれか
多分出品体験に関わる実装って2だけに見える。一番優先順位高いのにこれだけでいいの?

他に仮説／Actionってないか。最も優先順位高いactionがこれなのか?
例えば、
商品入力改善: 一括出品/CSV出品、バーコード/JANコードスキャン出品
出品判断を支援: 価格サジェスト(相場提示)、配送方法・送料の自動提案
出品後の体験改善: 価格変更・再出品サジェスト、出品パフォーマンスのフィードバック

上のように例えば、出品者の一連の体験を洗い出す。
まずはサイト上に商品情報を入力する ⇒ 価格等を決定するという判断があって ⇒ 実際に出品した後にその商品がどういうステータスかを確認するみたいなフローがある。それベースで整理してみるみたいな。
```

このサンプルは:
- Q1 では「スタンスを明確に」という冒頭の評価 → 各サブ論点（競合分析プロセス / 真贋判定 / シノニム辞書）に対する深掘り質問
- Q2 では候補者の論理を一旦受け止めて整理（「ファネル構造で...」）→ そのあとで「整理と scope が紐づいていない」と批判的に深掘り → 代替アクションの具体例を列挙 → 思考フレームの提示

この構造を真似て、課題の問いごとに「冒頭評価 → 深掘り質問 → 必要に応じて示唆／代替案／フレーム」のパターンで書く。

## 注意点

- **答えを述べない**: 候補者の代わりに正解を書くのではなく、候補者に考えさせる材料を提示する
- **詰問しない**: 批判的だが攻撃的ではない。「これだけだと弱く見えるが、何か他に考えていたか」のような、議論を開く書き方
- **回答に書いてないことを推測で批判しない**: 「書いていないが、こういう観点を考えているか?」と問う形にする
- **過度に多くの質問を作らない**: 面接60分で消化できる量に絞る。1つの問いに対して2〜5個程度
- **示唆セクションは必要なときだけ**: 答えを誘導しすぎないよう、本当に有益なフレームや具体例があるときだけ添える
