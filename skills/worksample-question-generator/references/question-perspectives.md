# 質問を作る観点 — 詳細リファレンス

3 グループ × 14 観点。各観点は「シグナル（回答・成果物に見えたら深掘りポイント）」「質問例」「見ていること」で構成する。

## 使い方の原則

- **観点タグは質問文ではなく「回答内の何に反応したか」で決める**。課題列挙で止まっていた → A4、比較なき断定 → A3、記述内の論理の飛び → A2、成果物間の不一致 → C4、のようにトリガーで振り分ける
- **A 群・B 群は常時適用**。C 群は該当する成果物があるときだけ当てる（データスキーマがあれば C1〜C3、ワイヤーフレーム・UI があれば C4）
- **B 群は回答スキャンとは独立に必ず生成する**。回答に取り組み方が書かれていなくても定型質問を質問リストに含める。成果物の具体箇所を引きながら肉付けできるとなお良い
- **2 段連鎖パターン**: C 観点で成果物の欠陥を指摘し → B3 でその受け止め方・立て直し方を観る、という連鎖を意図的に設計してよい

## A. 思考・スタンス — 回答本文の論理から発見する（常時適用）

### A1. スタンスの明確さ

自分が意思決定者だったら何をやるか、を打ち出しているか。意思の**有無**を見る（判断の**原理**は A6）。

- 「〜のため」「〜が望ましい」と書いているが、自分がやるなら何をやるかが書かれていない
- 「〜という方向で進めて良いでしょうか?」のような確認形のまま、自分のスタンスが薄い
- 「予想される課題」を列挙しているだけで、どう向き合うかが書かれていない

→ 質問例: 「実際に意思決定する立場にいるとして、どういうプロセス／ロジックで判断するか」

見ていること: 意見・立場を自分ごととして持てているか。

### A2. 論理接続

仮定→結論、優先順位→スコープの**ローカルな**論理接続（複数の判断をまたぐ軸のブレは A6）。

- 仮定 → 結論の間に論理が省略されている
- 優先順位や仮説と、実際のスコープ（MVP, ロードマップなど）の紐付きが薄い
- 「最も優先順位高い」と書いているが、それに紐づくアクションが少ない／弱い

→ 質問例: 「優先順位の整理と、実際のMVPのscopeがあまり紐づいていないように見える。一番優先順位高いのにこれだけでいいの?」

見ていること: 回答内の個別の論理接続の質。

### A3. 代替案の検討

選んだ施策の比較検討の広さ（自分で挙げた課題の突破は A4）。

- 提案された施策以外に、課題を解決する別アプローチを検討した形跡がない
- 「これが最善」と言える比較根拠がない

→ 質問例: 「他に仮説／Actionってないか。最も優先順位高いactionがこれなのか?」
→ **具体的な代替案を示唆として箇条書きで添える**（答えではなく、候補者が考慮すべきだった例として）

見ていること: 解空間をどれだけ広く見てから決めているか。

### A4. 行き詰まりの突破

- 「予想される課題」「現実的な課題」を列挙して終わっていて、どう乗り越えるかが書かれていない
- 業界の他社・競合がどう解決しているかへの言及がない

→ 質問例: 「これだけ見ると解決不可能な問題に見える。競合とかってどういうふうに対応してるのか」

見ていること: 課題を挙げた後に前へ進む力。

### A5. 実行計画の具体性

**提案施策**の実行計画（回答の中身）。候補者自身の作業の進め方は B1。

- 「人力で構築する」「AIで自動生成する」など抽象度の高い記述で止まっている
- 実際の運用・体制（人数）・期間・コスト・ガバナンスの想定がない

→ 質問例: 「実際に人間が辞書を構築するとしたらどういうプロセスになるのか?」

見ていること: 提案を実行に落とす解像度。

### A6. 判断軸の一貫性

- 判断の原理が言語化されておらず、ケースごとに判断がブレて見える
- 合理的な判断と現場の意見がコンフリクトするケースへの想定がない

→ 質問例: 「合理的な判断と現場からの意見がコンフリクトしたとき、どう判断するか」

見ていること: 自分の判断原理を言語化して、ケース差分があっても整合させられるか。理念と現場のズレの扱い（人の感情を考慮するなら、その位置づけまで含めて軸を再定義できるか）。

### A7. ユーザー体験の全体把握

テキストのみの回答にも当てる（UI 成果物との整合は C4）。

- 単発の機能で終わっていて、ユーザーの一連のジャーニー（入力 → 判断 → 確認）で整理されていない
- フロー全体での課題分解がない

→ 質問例: 「ユーザーの一連の体験を洗い出して、フロー別に整理してみる」
→ フローの例を示唆として添える（「商品情報を入力 → 価格を決定 → 出品後のステータス確認」など）

見ていること: 体験をフローで捉える視野。

## B. 進め方・セルフマネジメント — 課題への取り組み方を当日問う（常時適用・定型質問バンク）

### B1. 取り組みプロセスの再現性

課題そのものへの取り組み方（メタ）。提案内容の実行計画は A5、AI 出力物の品質判断は B2。

- 何から着手し、何を後回しにしたか／なぜかを問う
- 調査時間の有無、時間配分、アウトプットの組み立て順序を問う
- 曖昧さが出た瞬間にどう調べ、どう決めたかを問う

→ 質問例: 「ワイヤーフレームとスキーマ、どちらを先に設計したか? なぜ?」「あと2時間でブラッシュアップするなら、何をどんな順番でやる?」

見ていること: その場しのぎの結果ではなく、設計・実装・判断の再現可能性。

### B2. AI 活用の主体性

AI 出力物への品質判断（工程レベルの「いつ何に AI を使ったか」は B1）。

- AI をどこに使い、どこは自分で判断したかを問う
- AI が返したものを貼っただけになっていないかを探る

→ 質問例: 「この部分は AI にどう指示して、出力のどこを採用してどこを捨てたか?」
→ AI 生成物に簡潔化（共通化）やテストの切り出しなど改善観点でフィードバックし、その場の反応を見るのも有効

見ていること: 「なぜそうしたか」「どこを採用し、どこを捨てたか」を自分の言葉で説明できるか。

### B3. セルフレビューと指摘への応答

提出前の最終検証と、指摘を受けた後の対応。

- 設計・実装の抜け漏れを自分で検知できていたかを問う
- 抜け漏れや曖昧な設計を面接で指摘し、反応を観る: ミスを受け止められるか、原因を構造的に説明できるか（時間制約・チェック体制・思い込み等）、再発防止の仕組みを考えられるか
- AI を使う場合でも、最終成果物に対して自分の品質基準でレビューできているか

→ 質問例: 「（抜け漏れを指摘した上で）なぜ起きたと思うか。次に同じ課題をやるなら何を変えるか」

見ていること: プレッシャーに流されず冷静に自分の設計を見直せるか。C 観点の指摘とセットで反応を観る。

## C. 成果物の設計品質 — 成果物を検分する（該当成果物があるときだけ）

データスキーマがあれば C1〜C3、ワイヤーフレーム・UI があれば C4 を当てる。

### C1. データ設計の正しさと粒度

スキーマそのものの正しさ・粒度（量の変化への対応は C3、公開面のセキュリティは C2）。

- フィールドのデータ型は妥当か（例: IMEI が int になっているが桁落ちしないか）
- 冗長性を許容しているなら、その理由（可読性・JOIN コスト・実装都合等）を意図として説明できそうか
- テーブル分割・追加・省略の判断根拠。「省略した」部分は時間の都合か、本質的に不要と判断したか
- NULL 設計、RDBMS を採用した理由
- （余裕があれば）OLTP と OLAP でスキーマ戦略がどう違うか

→ 質問例: 「在庫にメーカーIDと機種IDが両方入っている必要ある?」「この設計を選んだ判断基準は何か。省略した部分は本当に省略して良いと判断したのか」

見ていること: それっぽい ER 図ではなく、運用上の事故（桁落ち・揺れ・結合の破綻）が起きない設計になっているか。

### C2. ID 設計と公開面のセキュリティ

- ID を連番／UUID 等にした理由が説明できそうか
- 連番 ID がユーザーに見える場所（URL・画面・API）に露出したとき何が起きるかの想定
- ID 以外のスキーマセキュリティ（PII の持ち方、認証情報の扱いなど）の考慮

→ 質問例: 「連番IDをユーザーに見せると何が起きる?」

見ていること: DB の都合だけでなく、ユーザーに見える世界（URL／画面／API）で何が起きるかまで想像できるか。

### C3. 規模変化への設計対応

- 規模が変わったとき（1日10件 vs 10万件）に設計のどこが変わるかの想定
- インデックスの基本理解（アルゴリズム、貼りすぎによる性能・書き込みコストの弊害）
- UI もビジネス規模によって適切さが変わる

→ 質問例: 「1日10件登録と10万件登録で、この設計はどう変わる?」

見ていること: 規模で設計判断が変わることを言語化できるか。過剰最適化ではなく必要十分に落とせるか。

### C4. UI の根拠と成果物間整合

- 画面選択の根拠が MVP のスコープと整合しているか。他にも候補となる画面があったはずなのに、なぜこれを選んだか
- UI 要素の配置・遷移の意図を説明できそうか
- データ設計の意図が UI に反映されているか: テーブルを分けたなら、正規化の価値（再利用・入力省略・揺れ防止）が入力導線・画面の選択肢設計に活きているべき

→ 質問例: 「この画面を選んだ理由を、MVPの優先順位と照らして説明できるか」「プロダクトとセールス情報の分離は良いが、ワイヤーフレームに再現されていないのはなぜ?」

見ていること: データモデルだけ綺麗 or UI だけそれっぽい、になっていないか。
