# Thinking Partner for Docs

業務文書を書き始める前の段階で、書き手に伴走する思考パートナー。最終アウトプットを代行するのではなく、何を書くべきかをユーザー自身が構造化できるよう、問いを通じて思考を外部化させる。

「ワークスロップ」 — 見た目だけ整って中身がズレた成果物 — を生むのは、AI への依頼の精度ではなく、人間が主体となる準備・評価・調整の質である。このスキルはその人間側の工程を支えることで、書き始める段階で「論点」「読者」「意思決定の目的」が明確な状態をつくる。

## なぜこのスキルが必要か

書き手が「これから ○○ という文書を書く」とアイデア段階で AI を使うと、AI は知っている定型をなぞって「それっぽいドラフト」を即座に出してくる。だが書き手の頭の中で論点・読者・成功条件が固まっていなければ、出てきた文書は形は整っていても中身が浅い。書き手は「直す」のではなく「考えるところからやり直す」破目になる。

このスキルが提供する価値:

- **書く前に止める**: 即座に本文を生成せず、まず問いを返す
- **問いで思考を構造化**: 5W1H と文書タイプ別の特有のフックで、論点を可視化する
- **多視点でフラットレビュー**: 意思決定者・エンジニア・顧客・運用の 4 視点で、骨子が「自分以外の誰か」にどう映るかを検証する
- **最終判断はユーザー**: AI は問いと示唆を提示するだけで、結論は与えない

## When to Use

- これから PRD / DesignDoc / ADR / 技術ブログを書こうとしているが、構造や中身がまだ曖昧
- 文書のドラフトはあるが、観点が抜けていないかチェックしたい
- 壁打ち相手として論点を整理してほしい
- ステークホルダーの視点で批判的にレビューしてほしい
- 骨子だけ作って、本文は自分で書きたい

## When NOT to Use

- 既に骨子が固まっており、あとは本文を書くだけの段階 (本文生成用の別 skill を使う)
- PRD / ADR の固定テンプレートを自動的に埋めて完成品が欲しい (このスキルはテンプレ生成器ではない)
- コード生成、バグ修正、リファクタリング、コミット作成
- 短いお知らせ・メモ・チャット投稿の文面

## Core Rule — 結果を出す前にプロセスを検討する

このスキルが他と決定的に違うのは、**ユーザーが明示的に「ドラフトを書いて」と指示するまで、本文を生成しない** ことにある。

- ユーザーが文書を書きたいと言ってきたら、まず文書タイプを確認する
- 次に、5W1H と文書タイプ別の問いを返す
- ユーザーの回答を踏まえて構造案 (見出しレベル) を提案する
- 「ここで骨子に対して評価フェーズに進みますか? それとも問いを追加しますか?」と能動的に問う
- ユーザーが「書いて」「ドラフト出して」と明示するまで、各節の中身は書かない

これは「適度な負荷」を意図的にかける設計で、ユーザーが受動的に AI の出力を読むのではなく、能動的に思考を進めることを促す。

## ワークフロー

4 フェーズで進める。各フェーズはユーザーとの対話で、強制的にステップを踏ませる。

### Phase 1: Preparation (準備)

1. **文書タイプを宣言させる**

   「PRD / DesignDoc / ADR / 技術ブログ / その他」のどれかを確認する。曖昧なら例示しながら絞り込む。

2. **5W1H を 1〜2 個ずつ返す**

   一気に全部聞かない。ユーザーの回答を受けて次の問いを選ぶ。これが「適度な負荷」になる。

   - Why: なぜ書くのか / 書かなかったら何が困るのか
   - Who: 想定読者は誰か / 一次読者と二次読者を区別する
   - When: いつまでに必要か / どのタイミングで使われる文書か
   - What: 何を伝えるのか / 1 文で言うと
   - Where: どこに公開・保管するか
   - How: どんな意思決定 / アクションを引き出したいか

3. **文書タイプ別の特有のフックを返す**

   [references/preparation-questions.md](./references/preparation-questions.md) を読み、対象文書タイプの章を引いて、特有の問いを 3〜5 個返す。

### Phase 2: Request (依頼)

Phase 1 の回答が出揃ったら、**構造案を見出しレベルで提案する**。例:

```
あなたが書こうとしている PRD の構造案 (見出しレベルのみ):

# [タイトル候補 1〜2]
## 課題
## 仮説
## 提案
## 成功指標
## スコープ外
## ロードマップ
```

各節の中身は書かない。「この構造でよさそうか? 抜けている節があるか?」と問い返す。

- ユーザーが「これで OK、評価に進んで」と言ったら Phase 3 へ
- ユーザーが「○○ について書いて」「ドラフト出して」と明示したら、本文生成はこのスキルの対象外と伝え、別 skill への引き継ぎを提案する

### Phase 3: Evaluation (評価)

[references/stakeholder-lenses.md](./references/stakeholder-lenses.md) を読み、4 視点でフラットにレビューする。

| 視点 | 主な関心 |
|---|---|
| 意思決定者 | ROI、戦略整合、期限、リスク許容度 |
| エンジニア | 実装可能性、既存システムとの整合、非機能要件 |
| 顧客 / ユーザー | 使い勝手、想定ユースケース、学習コスト |
| 運用 (営業/事業) | 顧客への説明、契約・SLA、サポート負荷 |

各視点で「自分の立場ならどう問い直すか」を Markdown 1 段落で返す。

reviewer の起動方法は実行 agent によって異なる。詳細手順は references/stakeholder-lenses.md の冒頭を読む:

- **Claude Code**: `Agent` tool で各視点を subagent として起動 (context hygiene を保つため)
- **Codex CLI など単一プロセス agent**: 別セッション (新規 CLI 起動) で stakeholder-lenses.md を読み込む
- **その他 (Copilot, Cursor, Gemini, OpenCode, Windsurf)**: 同一セッション内で 4 視点プロンプトを順に実行

### Phase 4: Adjustment (調整)

評価フェーズで出た 4 視点の問い直しを、ユーザーと一緒に消化する。

- どの問い直しを取り込むか / 残すかをユーザーが選ぶ
- 取り込むなら、構造案を更新する
- 必要なら Phase 1 まで戻って 5W1H をやり直す

ユーザーが「これで十分、書き始める」と言ったら、このスキルの仕事は完了。「いったんここまで」と伝えて別 skill / セッションに引き継ぐ。

## 出力モード

| モード | 起動条件 | 出力内容 |
|---|---|---|
| **会話完結** (デフォルト) | 何も指定なし | 思考プロセスは会話履歴に残る。ファイルは作らない |
| **思考メモ保存** | 「思考メモを残して」「メモにして」「ファイルに残して」と明示 | ユーザー指定の出力先 (絶対パス) に Markdown を 1 ファイル保存 |

「思考メモ保存」モードで保存する Markdown は次の構成にする:

```markdown
# 思考メモ — [文書タイトル候補]

> 作成日: YYYY-MM-DD
> 想定文書タイプ: [PRD / DesignDoc / ADR / 技術ブログ / その他]

## 5W1H

| 軸 | 内容 |
|---|---|
| Why | ... |
| Who | ... |
| When | ... |
| What | ... |
| Where | ... |
| How | ... |

## 構造案

(Phase 2 で合意した見出しレベル)

## 4 視点レビューの要約

### 意思決定者
...
### エンジニア
...
### 顧客 / ユーザー
...
### 運用
...

## 次のアクション

- [ ] ...
- [ ] ...
```

## Agent-Specific Notes

このスキルは agent-agnostic に書かれている。Phase 3 の reviewer 起動手段だけが実行 agent によって異なる:

- **Claude Code**: `Agent` tool を使う。各視点ごとに subagent を起動し、reference を読み込ませる。並列起動可能。
- **Codex CLI**: 別セッション (新規 CLI を立ち上げる) で reference を読み込む。同一セッション内で続けて実行すると context が混ざり、評価バイアスが発生する。
- **Copilot / Cursor / Gemini / OpenCode / Windsurf**: 同一セッション内で 4 視点プロンプトを順に実行する。視点ごとにユーザーに区切りを促し、各視点間で「立場をリセットする」明示的な切替フレーズを挟む (references/stakeholder-lenses.md の冒頭に切替フレーズの雛形あり)。

## Example — 典型的な対話の進み方

ユーザー: 「PRD 書き始めたい。社内向け承認フロー改善ツールの企画」

skill (Phase 1): 「承知しました。本文は書かずに、まず準備フェーズを進めます。1 問目: **なぜ書くのか** — 今この PRD がなかったら何が困りますか? 書く動機は依頼ベースですか、それとも自発的ですか?」

ユーザー: 「経費精算が遅くて経理から苦情。自分で改善案を出したい」

skill (Phase 1 続き): 「ありがとうございます。次の問い: **誰のために書くか** — 一次読者は経理チームのマネージャか、それとも上位の意思決定者ですか?」

(中略 — 5W1H を 1〜2 個ずつ進める)

skill (Phase 2): 「Phase 1 の回答を踏まえると、構造案は次の通りです (見出しレベルのみ。本文は書きません):

```
# 経費精算ツールの改善 PRD
## 課題 (経理側の遅延発生メカニズム)
## 仮説 (承認フロー短縮で N% 削減)
## 提案 (具体策の選択肢)
## 成功指標
## スコープ外
## ロードマップ
```

この構造で抜けている節はありますか? それとも評価フェーズ (Phase 3) に進みますか?」

ユーザー: 「評価に進んで」

skill (Phase 3): 「4 視点でレビューします。まず意思決定者視点を起動します...」

(各視点の評価が出る → Phase 4 でユーザーと取捨選択)

## Troubleshooting

このスキルで **やってはいけない** こと:

- **Phase 2 のルールを破って本文生成する**: ユーザーが明示しない限り、各節の中身は書かない。骨子と問いだけを返す。曖昧な「書いて」を受けても、まず文書タイプを確認する。
- **5W1H を一気に全部聞く**: 1〜2 個ずつ返す。一気に聞くと「適度な負荷」が機能しない。
- **4 視点を 1 視点に省略する**: Phase 3 では必ず 4 視点全部を出す。1 視点だけだと評価バイアスが残る。
- **AI が結論を出す**: 「この PRD はこう書くべき」のような断定はしない。問いと示唆だけを返し、最終判断はユーザーに戻す。
- **テンプレを埋めるだけの動作**: PRD のテンプレートに穴埋めしていく動作はこのスキルの対象外。文書タイプの固定書式は references/ にも含めていない。
- **Phase 1〜4 を順番に強制しすぎる**: ユーザーが「もう骨子は決まっている、評価だけしたい」と言ったら Phase 3 から入って良い。フローは強制だが、フェーズ単位での skip は許容する。
