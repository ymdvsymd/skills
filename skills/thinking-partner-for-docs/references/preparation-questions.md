# Preparation Questions

Phase 1 (準備) で使う問いカタログ。SKILL.md から参照され、ユーザーとの最初の対話で「適度な負荷」をかけるために使う。

問いは **一気に全部** 投げない。1〜2 個ずつ返し、ユーザーの回答を踏まえて次の問いを選ぶ。

---

## 1. 5W1H 共通フレーム

文書タイプを問わず、書く前に確認する基本フレーム。

### Why — なぜ書くのか

- この文書がなかったら何が困るのか
- 書く動機は何か (誰かから依頼された / 自発的 / 課題発見)
- 「書かない」という選択肢はあるか — あるとしたら何が代替するか

### Who — 誰のために書くのか

- 一次読者 (最初に読んでほしい人) は誰か
- 二次読者 (一次読者経由で読む人、または将来読む人) は誰か
- 一次読者と二次読者で関心がどう違うか
- 読者の前提知識のレベルは

### When — いつ必要か / いつ使われるか

- 完成期限はあるか
- どんな状況で参照される文書か (会議の前 / 決定の根拠として / 参考資料として / 後から検索される文書として)

### What — 何を伝えるのか

- 1 文で言うと何の文書か
- 一番伝えたい主張は何か (絞り込む — 1 つに)
- 何を「伝えない」と決めるか (スコープ外)

### Where — どこに公開・保管するか

- 公開先 (Linear / Notion / GitHub / Confluence / Slack channel / 社外公開)
- アクセス権限の制約
- 検索性が必要か (タグ・ラベル・カテゴリ)

### How — どんな意思決定 / アクションを引き出したいか

- 読者にどんな行動をとってほしいか (承認 / 議論 / 実装 / 周知 / 振り返り)
- 「読み終わった時にこの状態になっていてほしい」を 1 文で
- 文書を読んだ後の「次のアクション」は何か

## 2. 文書タイプ別フック

ここに挙げる文書タイプは **例示** であり、固定テンプレートではない。各タイプ特有の論点を網羅するための問いカタログとして使う。挙げていない文書タイプ (RFC、ポストモーテム、議事メモ、企画書 ...) でも、近いタイプを参考にして問いを組み立てる。

### PRD (Product Requirement Document)

- 解こうとしている **顧客課題** は何か / 課題の根拠 (定量・定性)
- 仮説: この機能 / プロダクトを出すと何が起きると考えているか
- **成功指標** は何か (どんな数字が動けば成功か)
- 競合や既存代替手段との **差別化** は何か
- 優先順位の議論 — なぜ今これか / 後回しの判断軸
- **スコープ外** を明示する (やらないこと)
- ロードマップ — Phase 1, 2, 3 の見通しがあるか

### DesignDoc

- 解決対象の **技術課題** は何か (現状の問題、可能なら定量化)
- 既存実装との関係 (何を壊し、何を残すか)
- **代替案** を 2〜3 検討したか / なぜ採用案を選んだのか
- 非機能要件 (パフォーマンス / セキュリティ / 可用性 / 監査)
- データモデルや API の互換性 (破壊的変更があるか)
- ロールアウト戦略 (feature flag、段階的展開、切替方法)
- 失敗時の **ロールバック手段**

### ADR (Architecture Decision Record — Michael Nygard 形式)

5 セクションが基本形:

- **Title**: 決定の識別子 (例: 「テスト基盤を Jest から Vitest に移行」)
- **Status**: proposed / accepted / rejected / deprecated / superseded by ADR-NNN
- **Context**: この決定が必要になった背景 / 問題 / 力学
  - 「なぜ今この決定が必要なのか」を 1 段落で
  - 制約条件 (技術的・組織的・期限) を列挙
- **Decision**: 採用する変更 / 方針を能動態で 1〜2 段落
  - 「私たちは ○○ する」という形で書く
- **Consequences**: この決定の **肯定的・否定的・中立的** 影響
  - 何が簡単になり、何が難しくなるか
  - 受け入れる代償 (trade-off)
  - 将来この決定を見直すきっかけ (何が起きたら見直すか)

ADR 向けの追加問い:

- 検討した代替選択肢は何か / 採用しなかった理由は
- Status は proposed か accepted か / 誰の承認が必要か
- この決定が **不可逆な範囲** はどこか
- 「○ヶ月後にこの選択が間違いだったと分かる」シナリオは想定しているか

### 技術ブログ

- 想定読者は **社内** か **社外** か (前提知識のレベルが変わる)
- why → what → how のどこに重点を置くか
- 読了時間の目安 (15 分 / 30 分 / 45 分)
- 「この記事を読んだ人に何をしてほしいか」 (試してほしい / 議論してほしい / PR を送ってほしい)
- 似た記事との **差別化** は何か (なぜあなたが書く意味があるのか)
- 公開後のフィードバック想定 (社内 Slack / コメント / DM — どこで議論するか)

### その他 (汎用)

- 「これを書く目的」を 1 文で言うと
- 似た文書を過去に書いたことがあるか / 参照できるテンプレや先行例があるか
- 「書き終えた時にどうなっていてほしいか」を 1 文で

## 3. 問いの選び方のヒント

- ユーザーが既に答えている内容を **聞き直さない**
- ユーザーの回答に矛盾・空白を見つけたら、その場で **掘り下げる** (例: 「成功指標は CTR と言ったが、Why の答えと整合するか? Why は売上改善だった」)
- 文書タイプを最初に確定させると、特有フックが選びやすくなる
- 1 回の応答で問うのは **2 問まで**。多すぎると認知負荷が上がりすぎて、適度な負荷が崩れる
- ユーザーが沈黙したり「うーん」と止まったら、問いが抽象的すぎるサイン。1 段具体例を添える
