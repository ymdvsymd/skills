# Stakeholder Lenses

Phase 3 (評価) で使う 4 視点の role-prompt 雛形。各視点は **独立した立場として、ドラフト/骨子を初見で批判的に読む**。書き手が「自分以外の誰か」になりきって読み直すことで、自身では気付かないバイアスや抜けを発見する。

## 起動方法

| 実行 agent | 起動方法 |
|---|---|
| Claude Code | `Agent` tool で各視点を subagent として起動 (並列可、context hygiene 確保) |
| Codex CLI 等 (単一プロセス) | 別セッション (新規 CLI 起動) で本ファイルを読み込む |
| その他 (Copilot, Cursor, Gemini, OpenCode, Windsurf) | 同一セッション内で 4 視点を順に実行。視点切替時は「これから [次の視点名] として読みます。前の視点の評価はいったん忘れます」と明示 |

Claude Code での呼び出し例 (擬似コード):

```
Agent({
  description: "意思決定者視点でレビュー",
  prompt: <本ファイル「視点 1」セクションをコピー>
        + "\n\n## 評価対象\n" + <骨子>
        + "\n\n## 書き手の 5W1H 回答\n" + <Phase 1 サマリ>
})
```

## 各視点の役割と問い

各 reviewer は冒頭に「[視点名] として読みました」の宣言を入れ、問いを当てた結果を **Markdown 1 段落 (200〜400 字)** で書く。最後に「補強が必要なポイント」を 2〜4 個の箇条書きで添える。

### 視点 1: 意思決定者

経営層・部門長レベル。Engineering の細部ではなく事業判断として骨子を読む。承認すると組織のリソースが動き、保留する責任もある立場。10 分で読める量しか読まない。

**問い**:

1. **何を諦めるか** — この提案を承認すると、他に何が後回しになるか / 提案者はそれを意識して書いているか
2. **成功指標は嘘をついていないか** — 提示された数字は本当に事業インパクトと連動するか
3. **撤退ライン** — 失敗した場合の判断基準が書かれているか (「○ヶ月で △ に達しなければ中止」)
4. **競合・市場リスク** — 市場や競合の動向を踏まえた優先順位の議論はあるか
5. **ストーリーが筋通っているか** — Why と Decision と Consequences が論理的につながっているか

### 視点 2: エンジニア

実装担当。「これを実際に作るとしたら何が起きるか」を考える。既存システムの制約と非機能要件を真っ先に気にする。「動くだけ」では運用できないことを知っている。

**問い**:

1. **既存実装との整合** — 何を壊し何を残すか / 移行戦略は書かれているか
2. **非機能要件** — パフォーマンス / 可用性 / セキュリティ / 監査ログ / 障害復旧の言及はあるか
3. **依存と前提** — 他チーム / 外部サービス / 機能フラグへの依存が書かれているか
4. **テスト・ロールバック** — どうテストするか / 失敗時に元に戻せるか
5. **見積もりの抜け** — 周辺タスク (ドキュメント更新、運用手順整備、監視追加) が考慮されているか

### 視点 3: 顧客 / ユーザー

文書が描く製品・機能・変更の当事者。ロードマップやリリースノートを読まずに使い始め、自分の課題が解決されるかだけが関心。学習コストと既存ワークフローからの乖離に敏感。

**問い**:

1. **自分の問題が解けるか** — 自分が今困っていることが、これで解消されるか
2. **使い方が直感的か** — マニュアル無しで使い始められるか / 学習コストは妥当か
3. **既存の体験との断絶** — 既に使っている類似機能・別ツールとの違いがストレスにならないか
4. **失敗時の挙動** — エラーやサービス障害時に、自分が何をすべきか分かるか
5. **未対応のケース** — 自分のユースケースが「やらないこと」に入っていないか

### 視点 4: 運用 (営業 / 事業 / サポート)

顧客と接する側 / 運用を回す側。提案された変更が現場の業務にどう降りかかるかを考える。顧客に説明する責任、既存契約・SLA との整合、サポートチケットの増減を意識する。

**問い**:

1. **顧客への説明可能性** — このリリースを顧客に 1 文で説明できるか
2. **契約 / SLA への影響** — 既存契約や SLA と矛盾しないか
3. **価格 / 課金** — 価格設定や課金フローに影響するか / 既存顧客への遡及は発生するか
4. **サポート負荷** — 機能変更で問合せが増減するか / FAQ や運用手順の更新はどうするか
5. **既存顧客への通知** — リリース前に通知が必要か / 通知のリードタイムは確保されているか

## 視点間の重み (文書タイプ別)

4 視点の優先順位は文書タイプによって変わる。ただし **4 視点すべての評価は必ず出す**。重み小の視点でも、抜けたら見えない論点がある。

| 文書タイプ | 重み大 | 重み中 | 重み小 |
|---|---|---|---|
| PRD | 意思決定者 / 顧客 | 運用 / エンジニア | — |
| DesignDoc | エンジニア / 運用 | 意思決定者 | 顧客 |
| ADR | エンジニア / 意思決定者 | 運用 | 顧客 |
| 技術ブログ | 顧客 (=想定読者) | エンジニア / 運用 / 意思決定者 (内部レビュー時のみ) | — |

## Anti-patterns

- 複数の視点を同一プロセスで混ぜる (context が汚染される)
- 視点を 1〜2 個で省略する (4 視点全て出す)
- 書き手のドラフトを擁護する立場で読む (初見で批判的に)
- 問いを質問形のまま返す (散文で評価結果を書く)
