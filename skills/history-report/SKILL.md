# History Report Generator

リポジトリの特定時期以降の変更を分析し、`.history/` ディレクトリに調査レポートを生成するスキル。

## When to Use

- ユーザーが `.history/` にドキュメントを追加したいとき
- 特定バージョン以降の変更をまとめて説明するレポートが必要なとき
- CHANGELOG の各項目を掘り下げた技術解説を作りたいとき

## How It Works

### Step 1: 引数の解釈と範囲の特定

ユーザーの入力から以下を判断する:

1. **起点の特定** — バージョン番号（`v1.10.0`）、日付（`2026-04-05 以降`）、CHANGELOG の見出しテキストなど、どれが与えられても対応する
2. **コミット範囲の確定** — CHANGELOG.md のリリース日、git tag、または git log の日付フィルタを使って、起点以降のコミット一覧を取得する
3. **終点** — 明示されなければ HEAD とする

範囲の解決順序:

1. `git tag` でバージョンタグを探す（`v1.10.0`, `1.10.0` など）
2. タグがなければ CHANGELOG.md のリリース日から日付を特定し、前バージョンのタグからの範囲 (`vPREV..HEAD`) を使う
3. タグも CHANGELOG もなければ `git log --since` で日付ベースのフィルタを使う

```bash
# タグがある場合
git log --oneline v1.10.0..HEAD
# タグがない場合（CHANGELOG の日付を利用）
git log --oneline --since="YYYY-MM-DD"
# コミット数が多い場合は要約統計も取得
git log --oneline --since="YYYY-MM-DD" | wc -l
```

### Step 2: 変更のグルーピング

コミット一覧と diff を分析し、変更を**テーマ別**にグループ化する。グルーピングの粒度は、1テーマあたり `.history/` フォルダ1つに対応するサイズが目安。

グルーピングの判断基準:
- コミットメッセージのプレフィックスや共通キーワード
- 変更対象のディレクトリ・ファイル群の近さ
- CHANGELOG.md にセクション分けがあればそれを尊重
- 単独で説明するに足る規模と一貫性があるか

- 各グループ内でコードベースにおいて**複数の意味を持つ用語**を特定する（例: "session", "client", "context", "event"）。そのような用語がある場合、ドキュメント上で初出時に明示的に「ここでの X は Y を指す。Z とは異なる」と注記し、以降のセクションでも混同が起きやすい箇所で再注記する

結果として `YYYY-MM-DD_topic-slug` 形式のフォルダ名リストと、各フォルダに含めるドキュメント種別を決定する。

### Step 3: 既存 .history/ のスタイル分析

生成前に、既存の `.history/` フォルダの中身を読んでスタイルを把握する。以下の特徴を踏襲する:

#### フォルダ命名

```
.history/YYYY-MM-DD_topic-slug/
```

- 日付はそのテーマに最も関連するコミットの日付（リリース日やマージ日）
- slug はハイフン区切りの英語小文字、テーマを端的に表す

#### ドキュメント種別

| ファイル名 | 用途 | いつ作るか |
|-----------|------|----------|
| `INVESTIGATION.md` | メインの調査レポート。何が変わり、なぜ変わり、どう動くか | 常に作成 |
| `DEEP-DIVE-*.md` | 特定サブシステムの詳細技術分析 | テーマ内に独立して深掘りすべきサブトピックがあるとき |
| `RUNBOOK.md` | 実践ガイド。ユーザーが手順に沿って操作できる形式 | 導入・設定・運用手順の説明が必要なとき |

#### INVESTIGATION.md テンプレート

```markdown
# [テーマタイトル] 調査レポート

**調査日:** YYYY-MM-DD
**対象バージョン:** [プロジェクト名] vX.Y.Z（コミット範囲情報）
**調査者:** Claude Opus 4.6
**対象領域:** [このレポートがカバーする範囲]

---

## 1. [vX.Y.Z / この期間] で何が変わったのか

[変更の全体像を散文で説明。箇条書きの羅列ではなく、
 なぜこの変更が行われたのか、どういう文脈があるのかを語る。
 その上で、主要な変更を3-5点にまとめて方向性を示す]

---

## 2-N. [各機能・サブシステム別のセクション]

[Mermaid 図、テーブル、コード例を交えて詳述]

---

## N+1. テスト状況

[テストの有無・結果・カバレッジ]

---

## N+2. 調査所見のまとめ

### 実装状態の総括

| 機能領域 | 実装状態 | ファイル数 | 備考 |
|---------|---------|-----------|------|
| ... | ... | ... | ... |

### 注目すべき設計判断

1. **[判断名]:** [なぜその判断が行われたか]
```

#### DEEP-DIVE テンプレート

```markdown
# [サブシステム名]: 詳細調査

**調査日:** YYYY-MM-DD
**対象バージョン:** [バージョン情報]
**調査者:** Claude Opus 4.6
**関連ドキュメント:** [INVESTIGATION.md](./INVESTIGATION.md)

---

## 目次

1. [エグゼクティブサマリー](#1-エグゼクティブサマリー)
2-N. [詳細セクション]

---

## 1. エグゼクティブサマリー
[このサブシステムの位置づけ・目的・現状を簡潔に]

---

## 2-N. [詳細分析セクション]
```

#### RUNBOOK テンプレート

```markdown
# [操作対象] ランブック

**作成日:** YYYY-MM-DD
**対象バージョン:** [バージョン情報]
**対象者:** [このランブックの想定読者]

---

## 目次

1. [前提条件](#1-前提条件)
2-N. [手順セクション]

---

## 1. 前提条件
[必要な環境・ツール・権限]

---

## 2-N. [段階的な手順]
```

RUNBOOK 生成時の追加ルール:
- **必須 vs 任意の明示**: セットアップ手順の冒頭に、ユーザーが実際に行う必要がある設定と、任意の追加設定を明確に分離するテーブルまたはセクションを置く。ユーザーが「自分は何をしなくてよいか」を即座に判断できるようにする
- **不要な作業の明示**: ユーザーが誤解しやすい「やらなくてよいこと」がある場合は、「重要: ○○は不要」と明示的に記載する

### Step 4: ドキュメントの生成

各テーマフォルダについて:

1. **フォルダを作成** — `.history/YYYY-MM-DD_topic-slug/`
2. **INVESTIGATION.md を作成** — メインレポート。以下のルールに従う:

   **情報収集:**
   - そのテーマに属するコミットの実際の diff やファイル変更を読み、動作を理解した上で説明する
   - `git diff` や `git show` で具体的なコード変更を確認する
   - Mermaid 図でアーキテクチャや処理フローを可視化する
   - テーブルで比較・一覧・状態を整理する

   **セクション構成ルール:**
   - **ユーザー視点の導入**: コマンドや機能を説明するセクションは、最初の1-2文でユーザーから見た目的・用途を述べてから技術詳細に入る（例: 「○○を確認するコマンド」「○○したいときに使う仕組み」）
   - **問題先行**: 複雑な内部機構のセクションは「なぜ必要か」→「何が難しいか」→「どう解決したか」の順で構成する。フィールドや関数の列挙から始めない
   - **設計判断の根拠**: 非自明なアーキテクチャ選択（例: スクリプトではなくサブエージェント、直接呼び出しではなく broker 経由）には、**選ばれなかった代替案**とその却下理由を書く
   - **具体例の付与**: 機能・コマンドのセクションには少なくとも1つの具体的な使用例（コマンド例、ワークフロー例）を含める

   **ステートフルな仕組みの記述ルール:**
   - 状態を持つ機構（ジョブ、セッション、キャッシュ、キューなど）を説明する場合、必ず以下の3点を網羅する:
     (a) 正常ライフサイクル（作成→利用→完了→クリーンアップ）
     (b) クリーンアップの仕組み（誰が、いつ、どう消すか）
     (c) クリーンアップが失敗した場合に何が起きるか（孤立レコード、ロック残留など）

3. **必要に応じて DEEP-DIVE や RUNBOOK を追加**

### Step 5: 生成計画の提示

実際にファイルを書く前に、生成するフォルダとドキュメントの一覧をユーザーに提示して確認を取る。

```
生成予定:

1. .history/2026-04-05_ecc2-control-plane-alpha/
   - INVESTIGATION.md — ECC 2.0 Alpha の制御プレーン全体調査
   - DEEP-DIVE-CONTEXT-GRAPH.md — 共有コンテキストグラフの詳細

2. .history/2026-04-01_operator-workflow-expansion/
   - INVESTIGATION.md — Operator ワークフロー拡張の調査

この構成で進めてよいですか？
```

## Writing Guidelines

文体とスタイルに関する重要なルール:

- **言語は日本語。** 技術用語・コード識別子・コマンド名は英語のまま
- **散文で説明する。** 箇条書きの羅列ではなく、文脈と理由を語る散文を基本とする。箇条書きは手順・一覧・比較にのみ使う
- **「なぜ」を書く。** 何が変わったかだけでなく、なぜその変更が必要だったか、どういう問題を解決するのかを説明する。特にアーキテクチャ選択には「代わりに X する方法もあるが、Y の理由で Z を選んだ」形式の根拠を付ける
- **用語の曖昧性を解消する。** コードベース内で複数の意味を持つ用語（session, context, client など）は、初出時に「ここでの X は Y を指す」と注記する
- **図は Mermaid。** ASCII アートではなく Mermaid 記法を使う。ノード内の改行には `<br>` を使う
- **コードは実際のリポジトリから引用する。** 推測でコード例を書かず、実際のファイルを読んで引用・要約する
- **関連ドキュメントへのリンク。** 同フォルダ内の他ドキュメントへは相対リンクで参照する
- **セクション間に `---` を入れる**
- **過度に楽観的な評価を避ける。** 未完成の機能は「未完成」と書く。問題点があれば率直に記述する

## Examples

出力ドキュメントの構造は `## How It Works` の Step 1〜Step 5 を踏襲する。代表的なテンプレートとして:

- **テーマ別調査レポート** — `# [テーマタイトル] 調査レポート` 形式 (`## 1. ... で何が変わったのか` 〜 `## N+2. 調査所見のまとめ`)
- **サブシステム詳細調査** — `# [サブシステム名]: 詳細調査` 形式 (`## 1. エグゼクティブサマリー` 〜 `## 2-N. 詳細分析セクション`)
- **操作対象ランブック** — `# [操作対象] ランブック` 形式 (`## 1. 前提条件` 〜 `## 2-N. 段階的な手順`)

## Troubleshooting

- **Important:** 既存 `.history/` のスタイル分析 (Step 3) を必ず実施する。既存と乖離したスタイルで出力すると、リポジトリの履歴記録ポリシーが不安定になる
- **Note:** タグが無い場合は CHANGELOG の日付を使い、CHANGELOG が無い場合はコミット日範囲を使う。コミット数が膨大な場合は要約統計のみで詳細は省略する
