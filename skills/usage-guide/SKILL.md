# Usage Guide Generator

リポジトリの現在の状態を分析し、`.usage/` ディレクトリに使い方ドキュメントを生成するスキル。
変更履歴を追う `history-report` とは対になるスキルで、こちらは「今このシステムをどう使うか」に集中する。

## When to Use

- ユーザーが `.usage/` にドキュメントを生成したいとき
- リポジトリの使い方をまとめたガイドが欲しいとき
- 具体的なユースケースや手順を列挙したドキュメントが必要なとき
- 新しくリポジトリを使い始める人向けのオンボーディング資料を作りたいとき
- 既存の `.usage/` ドキュメントを最新のコードに合わせて更新したいとき

## history-report との違い

この 2 つのスキルは対で使う。混同しないよう、判断基準を示す:

| 依頼の意図 | 使うスキル |
|-----------|-----------|
| 「最近何が変わった？」「v2.0 以降の差分を調査して」 | history-report |
| 「使い方をまとめて」「ユースケースを書いて」 | **usage-guide** |
| 「このツールのセットアップ手順を整理して」 | **usage-guide** |
| 「なぜこの設計になったのか調べて」 | history-report |

## How It Works

### Step 1: リポジトリの探索と分類

ドキュメントを書く前に、リポジトリが何を提供するシステムかを理解する。以下の情報源を優先順に分析する:

1. **README.md** — プロジェクトの説明、インストール手順、基本的な使い方
2. **パッケージメタデータ** — `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, `pom.xml` など。名前・バージョン・説明・依存関係
3. **コマンド/API 定義** — `commands/` ディレクトリ、CLI エントリポイント、ルートハンドラ、`bin` フィールド、argparse/clap 定義
4. **ソースコードのエントリポイント** — `main.ts`, `index.mjs`, `src/lib.rs`, `main.go` など
5. **設定ファイル** — `config.toml`, `.env.example`, `settings.json`, YAML 設定、スキーマ定義
6. **テストファイル** — テストは実際の使い方パターンを内包している。テストケースの名前と構造から利用シナリオを抽出する
7. **既存ドキュメント** — `docs/`, CHANGELOG, OpenAPI スペック、エージェント定義ファイル

探索の結果、システムを以下のいずれかに分類する。この分類で生成するドキュメントの構成が変わる:

| 分類 | 判断基準 | リファレンスファイル名 |
|------|---------|---------------------|
| CLI ツール / プラグイン | コマンド定義、bin エントリ、CLI パーサ | `COMMANDS.md` |
| ライブラリ / SDK | エクスポートされた関数・クラス、npm/crate としてのパッケージ | `API-REFERENCE.md` |
| Web サービス / API | ルートハンドラ、エンドポイント定義、認証ミドルウェア | `API-REFERENCE.md` |
| フレームワーク | 規約ベースのディレクトリ構造、ライフサイクルフック | `CONVENTIONS.md` |
| ハイブリッド | 上記の複合 | 該当するものを複数生成 |

### Step 2: 既存 .usage/ のスタイル分析

`.usage/` ディレクトリが既に存在する場合、既存ファイルを読んでスタイルや構成を把握する。新規生成時に既存の文体や構成を踏襲するため。存在しない場合はこのステップのテンプレートを使って新規生成する。

### Step 3: 生成計画の提示

ファイルを書く前に、生成するドキュメントの一覧をユーザーに提示して確認を取る:

```
生成予定:

.usage/
  OVERVIEW.md        — システム概要・主要機能・対象ユーザー
  QUICKSTART.md      — インストールから初回実行までの手順
  COMMANDS.md        — コマンドリファレンス（7コマンド、フラグ一覧付き）
  USE-CASES.md       — ユースケースシナリオ（6シナリオ）
  CONFIGURATION.md   — 設定オプション・環境変数
  TROUBLESHOOTING.md — FAQ・よくある問題と対処法

この構成で進めてよいですか？
```

ユーザーが不要なドキュメントを指定したらスキップする。追加要望があれば取り込む。

### Step 4: ドキュメントの生成

各ドキュメントをテンプレートに沿って生成する。すべてのドキュメントは `.usage/` ディレクトリ直下に置く（サブフォルダは作らない）。

生成時の重要ルール:

- **実際のコードを読んで書く。** README だけで済ませず、ソースコードを読んでコマンドの引数、デフォルト値、実際の動作を確認する
- **テストファイルからユースケースを抽出する。** テストの describe/it 文やテストデータは、開発者が想定した利用パターンそのもの
- **コマンド定義ファイルを網羅する。** `commands/` ディレクトリがあれば全コマンドを列挙し、フラグと説明を抽出する
- **推測で書かない。** 確認できなかった動作には「未確認」と明記する

### Step 5: 品質セルフチェック

生成完了後、以下を自己検証する:

- [ ] 全コマンド / 公開 API が COMMANDS.md（または API-REFERENCE.md）に記載されている
- [ ] すべてのコード例がリポジトリの実際のコードに基づいている
- [ ] 各ドキュメント間の相対リンクが正しい
- [ ] USE-CASES.md に最低 3 シナリオある（大規模プロジェクトでは 5 以上）
- [ ] コマンド例はコピペで実行可能な形式になっている
- [ ] 設定項目のデフォルト値がソースコードと一致している
- [ ] 過去の状態や変更履歴に言及していない（それは history-report の役割）

#### ユースケースの発見方法

シナリオは以下の情報源から発見する:

1. **README の Usage/Examples セクション** — 開発者が明示的に示したワークフロー
2. **コマンド定義** — 各コマンドの存在自体が最低1つのユースケースを意味する
3. **テストファイル** — 統合テスト・E2E テストは実際の利用フローをコードで記述している。テスト名や describe ブロックからシナリオ名を導出する
4. **エージェント/フック定義** — 「いつ発動するか」の条件がそのままユースケース
5. **設定ファイルのオプション** — 設定可能な項目は「こう変えたい」というニーズの証拠

#### ユースケースの分類

| カテゴリ | 内容 | シナリオ数の目安 |
|---------|------|---------------|
| Getting Started | 初回セットアップ・動作確認 | 1 |
| Core Workflow | 日常的に最も使う操作 | 2-3 |
| Advanced Usage | 機能の組み合わせ、パワーユーザー向け | 1-2 |
| Automation | CI/CD、Hook、定期実行 | 0-1 |
| Recovery | エラー発生時の対処・デバッグ | 0-1 |
| Administration | 設定変更・メンテナンス | 0-1 |

最低 3 シナリオ。大規模プロジェクトでは 5-8 シナリオを目安にする。

Recovery カテゴリの発見ヒント: エラーハンドリングのコードパス、try-catch ブロック、fallback ロジック、タイムアウト処理、リトライ機構がある場合は Recovery シナリオが有効。TROUBLESHOOTING.md と重複しないよう、Recovery は「操作の途中で問題が起きた場合のリカバリ手順」に焦点を当て、TROUBLESHOOTING は「環境やセットアップの問題」に焦点を当てて棲み分ける。

#### 難易度の基準

| 難易度 | 基準 |
|--------|------|
| 初級 | 単一コマンドで完結。前提知識不要 |
| 中級 | 複数コマンドの組み合わせ。オプション指定あり |
| 上級 | ワークフロー設計が必要。副作用やトレードオフの理解が前提 |

## Writing Guidelines

- **言語は日本語。** 技術用語・コード識別子・コマンド名は英語のまま
- **ユーザー視点で書く。** 「何ができるか」「どうすればいいか」を中心に。内部実装の詳細は省くか最小限に留める
- **散文で説明する。** 手順やリストが必要な場面以外は、文脈のある文章で書く
- **コード例は実行可能に。** コピペしてそのまま動くコマンドを書く。プレースホルダには `<角括弧>` を使い、実値で置換すべきことを明示する
- **図は Mermaid。** ノード内の改行には `<br>` を使う。ASCII アートは使わない
- **コードは実際のリポジトリから引用する。** 推測で例を書かない
- **ドキュメント間は相対リンクで参照する。** COMMANDS.md のアンカーを USE-CASES.md から参照するなど
- **セクション間に `---` を入れる**
- **過去の変更や歴史には言及しない。** 「v2.0 で追加された」のような記述は不要。今使えるかどうかだけが重要

## Quality Gate

納品前のチェックリスト:

- [ ] **網羅性:** 全公開コマンド / API がリファレンスに記載されている
- [ ] **正確性:** フラグ名、デフォルト値、挙動がソースコードと一致している
- [ ] **実行可能性:** すべてのコマンド例がコピペで動く形式になっている
- [ ] **ユースケース:** 最低 3 シナリオ（大規模プロジェクトでは 5 以上）
- [ ] **相互リンク:** 各ドキュメント間のリンクが正しく機能する
- [ ] **現在時制:** 過去の変更や将来の計画に言及していない
- [ ] **再現性:** 前提条件を満たせば、手順通りに操作すれば誰でも同じ結果を得られる
