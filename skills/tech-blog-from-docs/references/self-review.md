# Phase 5: Self-Review チェックリスト ★ 最重要

書き終えた直後に、**全項目を機械的に通す**。違反を見つけたら、出力前に直す。

このスキルの存在意義の半分はここにある。「だいたい大丈夫そう」で出力してはいけない。

本フェーズは内部で 2 段階に分かれる:

- **Phase 5a (項目 1〜8, 10〜14)** ── 文体・構造の自己レビュー。grep + 目視で「読みやすさ」「日本語の質」をチェック
- **Phase 5b (項目 9)** ── ファクトチェック (事実整合性)。記事中の事実主張をソース doc に対して grep で裏付け検証。本セッションで判明したハルシネーション (`waza dev --model ...`、`--format detailed`、"post-merge が妥当" など) を出力前に潰す目的

両者をまとめて Phase 5 とし、すべてを通過してから Phase 6 (出力) に進む。

## チェック手順

1. 記事ファイルを Read で全文読み直す（書いている途中の自己評価に頼らない）
2. 下記 **14 個** のカテゴリを上から順にチェック (項目 1〜8, 10〜14 → Phase 5a、項目 9 → Phase 5b)
3. 違反が見つかったら、Edit でその場で直す
4. **各項目で違反を直したら、必ず全文を再 grep して同パターンの残存が無いか確認する** ── 「1 箇所だけ直して終わり」にしない (本セッションで `rubric` が 3 箇所、ルー語が複数パターンで残った教訓)
5. すべて通過してから Phase 6（出力）に進む

## チェックリスト

### 1. 専門用語の前振り欠如

**症状**: 初出の専門用語が、何の説明もなく文中に登場している。読者が「これは何？」で止まる。

**対象**: 単なる英術語・頭字語に限らず、次のすべてを含める:

- 大文字のキーワード (`Promise 2`, `Pipeline`, `Hook` 等)、英語術語、頭字語 (`MCP`, `SBOM`, `SLSA` 等)
- **JSON / YAML フィールド名** (例: `skill_impact.delta`, `pass_rate_baseline`, `outcomes`, `behavior.max_tool_calls`)
- **CLI フラグ・サブコマンド** (例: `--baseline`, `--auto`, `waza new task from-prompt`)
- **コード識別子・内部名** (例: `SkillPaths`, `RequiredSkills`, `set_waza_grade_pass`)

**検出方法**:
- 上記の対象パターンを grep
- それぞれが初出する箇所を特定
- 初出時に定義 or 後続節へのリンク or 1 行説明があるか確認

**修正パターン**:
- 「これは APM が公式に掲げる "Secure by default"（後述する "3 つの約束" の 2 つ目）の中核機能だ」のように、後続節へのブリッジを 1 句入れる
- Why セクション末尾に「補足: X 自身が掲げる "○つの約束"」のような対応表を追加し、以降の本文で内部用語を使えるようにする
- JSON フィールドは「`delta` は `pass_rate_with_skills − pass_rate_baseline` の絶対差分 (−1.0 〜 +1.0)」のように **意味と式と取りうる範囲** を 1 文で添える

**本セッションの実例**: 
- 「これは Promise 2 と呼ばれる仕様の中核機能。」と書いて、「Promise って何？」と指摘された
- `skill_impact.delta` を JSON サンプルに出したが意味を書かず、「delta とは？」と指摘された

### 2. 仕組み説明の曖昧さ

**症状**: 「自動で X する」「うまく Y される」「いい感じに Z」「heuristic に〜」だけで終わっており、how の具体性が無い。

**検出方法**:
- 次の語彙を grep:
  - 「自動」「自動的」「うまく」「いい感じ」「適切に」「よしなに」
  - 「heuristic」「魔法のように」「シンプルに言うと」「要するに」「基本的に」「ある種」
  - 「いろんな」「色んな」「様々な」 (修飾語が曖昧)
- 該当箇所が「結果だけ書いて手順を書いていない」状態か判定

**修正パターン**:
- 配置場所 → 取得経路 → キャッシュ → 適用タイミング の 4 フェーズで手順を具体化
- 番号付き箇条書きで「1. X から Y を抽出 → 2. Z を呼ぶ → 3. ~ に保存 → 4. ~ で適用」のように分解
- 「heuristic に X」と書きそうになったら、具体的なアルゴリズム名・データ源・スコアリング方法を 1〜2 文で書く

**本セッションの実例**:
- 「`apm install` はそれを自動取得する」と書いて、「具体どのように自動取得するのか分からない」と指摘された
- 「`trigger` grader が `SKILL.md` から keyword/phrase を抽出し、各 prompt との関連度を算出する」と書いて、「LLM 使わずどう抽出するか？」と指摘された。修正版では「LLM を一切使わず、skill 名・description・本文の見出し・USE FOR フレーズをトークナイズしてキーワード集合と候補フレーズに展開し、(a) prompt 側のトークンとキーワード集合の重複度、(b) prompt と USE FOR フレーズの最良フレーズマッチスコア、の高い方を最終スコアとする」と具体化

### 3. 図の解釈の二義性

**症状**: Mermaid 図のノードが「ファイルシステム」とも「組織内リポジトリ群」とも「クラウドリソース階層」とも解釈できる。読者が想定外の構造として理解する。

**検出方法**:
- 図の各ノードについて「これは何を表しているか」が一意か確認
- 根のノードが組織なのかリポジトリなのかディレクトリなのか、明示されているか
- Mermaid のノードラベルに「Repository:」「Directory:」「Service:」のような種別プレフィックスを付けると曖昧さが解消することが多い
- 図の中で改行したいときは `<br>` を使うこと（`\n` ではない）

**修正パターン**:
- ノードに `Repository: foo/bar` のように種別ラベルを付ける
- 図の前に「これはモノリポではなく、〜の話だ」と一文で前置きする
- 図の後に「ノード X は ~ を意味する」と注釈する

**本セッションの実例**: `acme/` 配下に `.github/`, `web-app/`, `api-server/` を並べた図を見せて、「モノリポに見える」と指摘された。修正版では「`GitHub Organization: acme`」「`Repository: acme/.github`」のように種別ラベルを各ノードに明示した。

### 4. 節内の重複・冗長性

**症状**: 同じ節内で、別の小節として同じ話を 2 回している。追記で膨らんだ結果、節がくどくなっている。

**検出方法**:
- 各節のサブセクション見出しを並べて読み、トピックが重複していないか確認
- 1 つの小節 = 1 つのトピックの原則が守られているか

**修正パターン**:
- 「単なるコンシューマー」「プロジェクト側に何も置かない」のような近い話は **1 つの節に統合**
- 各小節の役割を明確化（「配置」「中身」「継承」「落とし穴」「微調整」「観察」のように 1 節 1 機能）
- どうしても触れたい話は「落とし穴」「よくある質問」のような共通の節に集約

**本セッションの実例**: ユースケース ⑦ で「ポリシーはどこに置き、どう届くのか」と「単なるコンシューマーにもポリシーは効くのか」が話していることが近く、追記でくどくなった。後者を前者の中の 1 段落に圧縮した。

### 5. ルー語（英単語の不適切な日本語化）

**症状**: 英単語に日本語の活用語尾や接尾辞を付けて使う、または訳語が定着している英単語を地のままで使う。「gate される」「rubric ベース」「TDD-like」「literal にチェック」「reliability」など。

**検出方法**: 次のすべての grep パターンを **順に** 走らせる。ヒットした全件を **目視で精査** する (パターンによっては false positive が多い):

```bash
# 1. 英動詞のサ変動詞化
grep -nE '[a-zA-Z][a-zA-Z\-]+ (する|される|した|され|されて|して|させる|していく|していた|できる|できない)' <file>

# 2. 英単語 / カタカナ + 化された / 化する (両方カバー)
grep -nE '([a-zA-Z]+|[ァ-ヶー]+)化(された|する|して|されて)' <file>

# 3. 英単語 + ベース / 的 / 風 / -like / ライク
grep -nE '[a-zA-Z]+ (ベース|的|的な|的に|風|風に|ライク|っぽい)|[a-zA-Z][a-zA-Z\-]*-like' <file>

# 4. 英単語 + に + 動詞 (英単語の副詞化、後続は漢字 / かな / カタカナ動詞すべてカバー、「に」と動詞の間にスペースは入らない)
grep -nE '[a-zA-Z]+ に[一-龯ぁ-んァ-ヶー]' <file>

# 5. 訳語が定着している英単語の地のまま使用 (要目視判定)
# reliability, infrastructure, complexity, capability など、文中で目立つ大きな英単語を grep して、訳語があるか判定
grep -oE '[a-zA-Z][a-zA-Z]{6,}' <file> | sort -u
```

**false positive に注意** (検出件数が多くても全部 NG とは限らない):

- **パターン 3 (英単語 + 的)** ── 日本語化された頭字略語 + 「的」は **OK** で false positive: 「TDD 的なリズム」「CI 的な仕組み」「ML 的アプローチ」等。`TDD-like` `CI-like` は NG だが、`TDD 的` `CI 的` は許容範囲
- **パターン 4 (英単語 + に + 動詞)** ── 識別子 / ファイル名 / 固有名詞の後ろに助詞「に」が来る正当用法が大量に混じる: 「`eval.yaml` に追加」「`microsoft/skills` に PR を出す」「`SKILL.md` に書き込む」等。これらは **OK**。本来の NG は「literal にチェック」「graceful に終了」のような **英単語が副詞として機能している** ケースのみ
- **パターン 5 (長めの英単語)** ── 技術用語 (`microsoft`, `github`, `claude`, `kubernetes`, `frontmatter` 等) は OK。NG は **既に定着した日本語訳語がある語** (reliability, observability, maintainability 等)

つまりパターン 3 / 4 / 5 は **検出ゼロを目指すのではなく、ヒット件を 1 件ずつ目視判定し、副詞化されているもの・訳語が定着している語のみ修正対象とする**。パターン 1 / 2 はほぼ確実に NG なので、ヒットしたら全件修正。

**修正パターン**:
| NG | OK |
|---|---|
| gate される | ゲートにかける / 関門で止まる |
| scan する | スキャンする（カタカナで日本語化されている） |
| pin する | 固定する / ピン留めする |
| fan-out する | 展開する / 配信する |
| embed する | 埋め込む |
| **コード化された rubric** | 機械可読な採点基準 |
| **rubric ベース** | 採点基準に基づく / ルーブリックに基づく |
| **echo 的な動作** | エコーバックする動作 |
| **TDD-like なリズム** | TDD 的なリズム |
| **literal にチェック** | 文字どおりに照合 |
| **reliability** | 信頼性 |

判定軸: **そのカタカナ語が日本語として既に流通しているか**。「インストール」「スキャン」「コンパイル」は OK。「ゲート（する）」「ピン（する）」「リライアビリティ」は NG。

**全文再 grep のリマインド**: 1 箇所のルー語を直したら、**必ず上記 5 パターンすべてを全文に対して再 grep** する。本セッションでは "コード化された rubric" を直した後も "rubric ベース" "TDD-like" "echo 的" "literal に" "reliability" が残っていて、ユーザーから「全体見ろ」と複数回再指摘された。

詳しくは `japanese-writing.md` 参照。

**本セッションの実例**: 「ファイル書き出し前に gate される」「コード化された rubric」「rubric ベース」「TDD-like なリズム」「echo 的な決定動作」「literal にチェック」「特定モデルの reliability」── すべて指摘で直した。

### 6. 箇条書きの文末スタイル不統一

**症状**: 1 つの箇条書きグループ内で「~せよ」「~こと」「~する」「名詞句」が混在している。

**検出方法**: 箇条書きを 1 つずつ目視確認。各項目の末尾形式を並べてみて、揃っているか確認。

**修正パターン**: 全項目を 1 つのスタイルに統一する。
- 検証項目・要件列挙 → 「~こと」体言止め
- 手順・操作列挙 → 「~する」動詞句
- 短い項目列挙 → 名詞句

**本セッションの実例**: `apm audit --ci` の 8 baseline check の説明で、項目によって「YAML 構文と APM スキーマ」（名詞句）、「存在せよ」（命令形）、「無いこと」（体言止め）、「lockfile と照合」（名詞句）が混在していた。全項目を「~こと」体言止めで統一した。

### 7. サンプル名の不整合

**症状**: 組織名・パッケージ名・ユーザー名のサンプルが、記事内で複数バリエーション混在している（例: `contoso` と `acme` が章をまたいで混ざる）。

**検出方法**:
- `grep -oE 'github\.com/[a-z0-9-]+' file.md | sort -u` などで組織名のバリエーションを列挙
- 同様にパッケージ名のパターンも

**修正パターン**: 記事全編で 1 つのサンプル組織名に統一する。`acme` を選んだら全編 `acme`。`contoso` も `example-org` も混ぜない。

**例外**: 「複数組織を使い分ける」例を示したいときは、`acme` と `contoso` を併記する明確な意図がある場合に限り OK。

**本セッションの実例**: ユースケース ⑦ で組織レイアウト図は `acme/`、YAML 例の中身は `contoso-baseline` になっていて、章を読み進めると整合性が崩れていた。全部 `acme` に統一した。

### 8. 文字数と読了時間目安の整合

**症状**: 「30 分で読める」と冒頭で予告したが、実際は 50 分かかる分量、あるいは 15 分しかない分量。

**検出方法**:
- `wc -m <file>` で総文字数をカウント
- 600 字/分換算で読了時間を概算
- リードで宣言した読了時間と ±20% 以内に収まっているか

**修正パターン**:
- 多すぎる → ユースケースを 1〜2 個削るか、深掘りパートを参考リンクに逃がす
- 少なすぎる → 補足節・落とし穴節・「明日試すコマンド」を追加
- どうしても削れない場合は、リードに「想定読了 30 分 (コード飛ばし読み時) / 45 分 (精読)」のように 2 段表記する手もある

### 9. ファクトチェック ★ Phase 5b (最重要・新規)

**症状**: 記事中に書いた具体的な事実主張 (コマンド・フラグ・数値・YAML フィールド・JSON 出力例・運用 tips) が、ソース doc に存在しない。subagent の研究結果や自分の推測由来で「もっともらしい」が **実在しない情報** を書いてしまう (= ハルシネーション)。

**特に危険な箇所**: 次の 7 カテゴリは subagent 報告や推論を信じやすく、ハルシネーションが混入しやすい:

1. **コマンド / サブコマンドの存在と引数の取り方** (`waza dev` が何を引数に取るか、など)
2. **フラグ名と取りうる値** (`--format` の値が `table` / `json` / `detailed` のどれか、など)
3. **数値・閾値** (token budget の数値、specificity scoring の係数、コンプライアンス基準の文字数、など)
4. **YAML / JSON スキーマのフィールド名** (`tokens.warningThreshold`, `trigger_tests.yaml` の `confidence` フィールド、など)
5. **アーキテクチャ的主張** ("Sensei は rubric ベース"、"Copilot SDK は LFS で embed されている" 等の構造的事実)
6. **出力例の verbatim 引用** ("Pass Rate: 85.0%" のような JSON / Box 表示の具体値、フィールド名、ASCII 装飾)
7. **運用 tips・主観的提案** ("post-merge job が妥当"、"PR の必須チェックにすべき" 等の **「妥当」「現実的」「推奨」「ベスト」を含む文**)

**検出方法**:

1. **記事中の具体的な事実主張を列挙**:
   ```bash
   # コマンドとフラグの抽出
   grep -nE '^waza |waza [a-z]+ |--[a-z\-]+' <article> | sort -u
   # 数値・閾値の抽出
   grep -nE '[0-9]+ (token|chars|文字|個|秒|分)|[0-9]+\.[0-9]+|\+?[0-9]+%' <article>
   # YAML フィールド名の抽出
   grep -nE '^\s*[a-z_][a-z_]*:' <article>
   # 主観 tips の検出
   grep -nE '妥当|現実的|推奨|ベスト|定石|王道' <article>
   ```

2. **各主張がソース doc に存在するか grep で検証**:
   - 引数で渡されたソース doc 一式 (`<source-dir>/**/*.md`) に対して、抽出した固有名詞・数値を grep
   - 1 ヒット以上あれば OK、ゼロヒットならハルシネーション疑い
   - 「ソース doc に類似はあるが微妙に違う」(例: ソースは `--target medium-high` を取るが記事は `--model claude-sonnet ...` と書いている) は **DISTORTED** 扱いで要訂正

3. **subagent 報告はソースではない**:
   - Phase 2 の subagent 研究結果に含まれる固有のコマンド / フラグ / YAML 例は、**必ず一次ソース** (引数で指定された md ファイル) で再確認する
   - subagent はハルシネーションする (本セッションでは subagent 由来の `waza dev --model ...` `--format detailed` 等が混入した)

4. **主観 tips は設計意図と矛盾していないか確認**:
   - 「妥当」「現実的」「推奨」と書いたものは、ソース doc の design / PRD / CHANGELOG にその意図と矛盾する記述がないかチェック
   - 本セッションでは「`--baseline` を post-merge job として運用するのが妥当」と書いたが、`design/194-baseline-skill-impact.md` の意図は「マージ前 gating」であり矛盾していた

**修正パターン**:

- ハルシネーション確認 → **削除**、または「(本記事の推測)」「(ソース doc に明示なし)」と明示
- DISTORTED 確認 → ソースの記述に揃える
- 主観 tips が設計意図と矛盾 → 撤回して書き直す。書き直した後も同じ問題を抱えないか再確認 (折衷案で問題を覆い隠さない、項目 14 を参照)

**本セッションの実例**:

| ハルシネーション | 実態 |
|---|---|
| `waza dev evals/.../eval.yaml --model ...` | `waza dev` は `[skill-path]` を取る。`--model` は `--copilot` 非対話モード限定 |
| `waza compare --format detailed` | `--format` の値は `table` / `json` のみ。`detailed` は存在しない |
| 「post-merge job として運用が妥当」 | design/194 の意図は「マージ前 gating」 |
| 「グレーダーは 12 種類」 (subagent は 11 種類と主張) | graders/README.md の not-implemented マーク付きは 6 種、18-6=12 で記事が正しかった (subagent の誤判定だった事例) |

最後の事例は重要: **subagent のファクトチェックも信頼できない**。一次ソースで自分で確認する。

### 10. 名詞-動詞の意味的整合 (目視)

**症状**: 動詞の主語または目的語が、その動詞を意味的に取れない。文法上は破綻していないが、意味が通らない。

**検出方法**:
- 全文を文単位で読み、各動詞について「この動詞は本当にこの主語/目的語と組み合わせて意味が成立するか」を確認
- 機械検出は困難。読み返しでしか拾えない

**よくある NG パターン**:
- 「<工程> に <備わる/揃う>」 ← 「工程」は備わる主体になりにくい
- 「<ファイル> の隣を探索」 ← ファイルに「隣」という空間概念は成立しない
- 「<時間> が <持ち上げる>」 ← 抽象名詞を主語に物理動詞を置く

**修正パターン**:
- 主語または動詞を、意味的に咬み合うものに置き換える
- 例: 「Skill 工程にはまだ揃っていない」→「Skill 開発の側にはまだ備わっていない」(対比語との整合も取れる)
- 例: 「eval.yaml の隣を探索」→「eval.yaml と同じディレクトリにある〜を検出」

**本セッションの実例**: 「Skill 工程にはまだ揃っていない」(指摘) → 「Skill 開発の側にはまだ備わっていない」(修正)

### 11. 比喩・訳語の適切性 (目視)

**症状**: 文脈に合わない訳語 / 造語 / 空間比喩 / 視覚比喩を使い、読者が意味を取れない。

**検出方法**:
- 全文を文単位で読み、英術語の訳語、無理な日本語化、比喩表現を確認
- 機械検出は困難

**よくある NG パターン**:
- **無理な比喩**: 実行記録を「録画」(ビデオ的)、ファイル探索を「隣を探索」(空間的)、フィルタを「ふるい」(漁網的) など、文脈に合わない比喩を使う
- **無理な造語**: 適切な訳語が無いからといって「偽 tool」「擬似 grader」のような不明瞭な造語を作る

**修正パターン**: 適切な訳語が見つからない場合の **3 つの逃げ道**:

1. **英語のまま + 補足説明**: 「`set_waza_grade_pass` / `set_waza_grade_fail` という 2 つの判定伝達専用 tool を差し込む。これらは外部に副作用を起こす本物の tool ではなく、judge model の判定結果を構造化シグナルとして渡すためのインターフェース」のように、英語のまま + 何のためかを 1 文で補足
2. **既存の自然な日本語句に組み替え**: 「録画」→「記録するのは 1 回の実行分のみ」、「隣を探索」→「同じディレクトリにある〜を検出」
3. **文構造を組み替えて訳語自体を不要にする**: 比喩の必要性そのものを再評価

**本セッションの実例**:
- 「録画は 1 回の実行に対して行われる」→「from-prompt が記録するのは 1 回の実行分のみ」
- 「eval.yaml の隣を探索」→「eval.yaml と同じディレクトリに置いておくと、waza run がそれを検出」
- 「偽 tool を差し込む」→「判定伝達専用 tool を差し込む。これらは外部に副作用を起こす本物の tool ではなく、〜のためのインターフェース」

### 12. 主体/客体・関係性の明示 (目視)

**症状**: テスト入力なのかテスト対象なのか、入力なのか出力なのか、生成側なのか消費側なのかが文中で曖昧で、主客が逆転して読める。

**検出方法**:
- 「<A> を増やす / 変える / 追加すると <B> が〜する」のような相関を述べる文を全文で確認
- A が原因側 (=操作される側) で B が結果側 (=観察される側) の関係が、読者にとって一意に解釈されるか確認
- 機械検出は困難

**よくある NG パターン**:
- テスト入力集合 (例: `should_trigger_prompts`) に「Explain」など語彙を増やすと、本来 SKILL.md 側 (`description`) が試される話なのに、SKILL.md がより発火しやすくなる、と誤読される書き方をする
- データフロー (入力→処理→出力) を逆向きに書いて主客が逆転する

**修正パターン**:
- 文の冒頭で **「これはテスト入力側」「これはテスト対象側」** のように役割を明示
- 「A を増やすと B が活性化する」のような相関の方向性を明文化
- 失敗例 / 浮かび上がる事象を 1 句で具体化 (例: 「`Explain` には反応するが `Walk me through` には反応しない、という穴が浮き彫りになる」)

**本セッションの実例**: 
- 「`should_trigger_prompts` を増やすときは、表現バリエーション (直接的 / 暗示的 / 文脈依存) を意図的に散らす。同義表現に対する頑健性をテストできる」 ← 「Explain を含めると発火しやすくなるのか?」と混乱させた
- 修正版: 「`should_trigger_prompts` は **テストプロンプト集合** である。ここに「Explain this」「Walk me through」のような直接的/暗示的/文脈依存表現を意図的に散らして並べておくと、SKILL.md の description や USE FOR セクションが「同じ意味の表現の揺れ」に対してどこまで活性化を拾えるかを網羅的にテストできる。skill 側ではなくテスト入力側を多様化することで、SKILL.md の文面の穴 (例: Explain には反応するが Walk me through には反応しない) が浮き彫りになる」

### 13. 分類スキーマの明示 (目視)

**症状**: 記事内で分類軸 (個人 / チーム / 組織、初級 / 中級 / 上級、フロントエンド / バックエンド 等) を使ってラベル付けしているのに、何種類でどんな基準かを冒頭で説明していない。読者は読み進めながらラベルの意味を逆算することになる。

**検出方法**:
- ユースケース・章・サンプルに付けたラベルを列挙
- 種類数と基準が記事のどこで定義されているか確認
- 定義が無ければラベルを使う直前の段落で明示する

**修正パターン**:
- ラベルを使う直前のセクション (How の導入段落など) で、3〜4 種類のラベルとその基準を表で示す
- 境界例は「個人/チーム」のように **斜線併記** で表現し、新ラベルを増やさない
- 並び順 (個人 → チーム → 組織 など) も明示し、読者の関心の広がり方向と合わせる

**本セッションの実例**: 「個人」「チーム」「組織」「個人/チーム」「チーム/組織」とラベル付けしたが、種類数と基準が冒頭になく「これは何ラベルあるのか?」と質問された。修正版では How 導入段落に「3 ラベル + 斜線併記」のルールを表で明示

### 14. 折衷案で問題を覆い隠していないか (目視)

**症状**: 「コスト vs 効果」「速度 vs 安全」のようなジレンマがあるとき、両極のどちらも取らずに **中間提案** を書いて、結果としてどちらの目的も達成できない案を出している。

**検出方法**:
- 「〜なら良いが」「〜してもよい」「PR 必須チェック以外の方法もある」のような **折衷を提案する文** を見つける
- その提案が、もともとの問題 (例: バグ混入防止) を本当に解決しているか確認

**よくある NG パターン**:
- 「実行時間 2 倍が痛いので、ラベル付き or 手動起動 or nightly で頻度を抑える」 ← ラベル忘れ / 起動忘れ / nightly 待ちの間にマージ、で全て gating として機能しない
- 「セキュリティと利便性のバランスを取って、適度に〜する」 ← 何が「適度」か不明、結果として穴ができる

**修正パターン**:
- ジレンマがあることを **正直に書く**: 「これはトレードオフであり、どちらかを取るしかない」
- 中庸案を出す前に「この中庸案で本来の問題が本当に解けるか」を自問する
- 解けないなら、トレードオフを書いて読者に判断を委ねるか、そのトピック自体を削除する

**本セッションの実例**: 
- 初版: 「`--baseline` は実行時間が 2 倍。CI 全実行に組み込むと痛いので、main マージ後の post-merge job として運用するのが妥当」 ← 設計意図と矛盾
- 第 2 版: 「PR ラベル付き / 手動起動 / nightly で頻度を抑えつつマージ前 gating」 ← どれも gating として機能しない
- 最終版: bullet 自体を削除 (当たり前の話に希釈されたため)

### 15. 表記揺れ (カタカナ vs 英語の混在)

**症状**: 同じ技術概念を、記事内でカタカナと英語の両方で書いて混在させてしまう。読者は「両者は別物か?」と止まる、または記事の品質を疑う。

**典型例**:

- 「グレーダー」と「grader」が混在
- 「ルーブリック」と「rubric」が混在
- 「ハーネス」と「harness」が混在
- 「マニフェスト」と「manifest」が混在
- 「ライフサイクル」と「lifecycle」が混在

**検出方法**:

1. 記事で頻出する技術概念名を特定 (記事冒頭のプリミティブ表、繰り返し出てくる名詞、章タイトルから列挙)
2. 各概念について、カタカナと英語の両表記を grep:

   ```bash
   grep -nE 'グレーダー|grader' <file>
   grep -nE 'ルーブリック|rubric' <file>
   grep -nE 'ハーネス|harness' <file>
   ```

3. ヒットしたら記事内で **方針が一貫しているか** 確認。混在していたら統一する

**方針判定パターン**:

技術記事で実用的な方針は次の 2 つ。記事冒頭または What セクションで明示する:

- **A. 識別子付き/無冠の区別 (推奨)** ── 「`<name>` + 英語」(識別子付き) と「カタカナ単独」(無冠総称) を使い分ける
  - 例: 「`code` grader、`prompt` grader」(識別子付き) と「実装済みのグレーダー 12 種類」(無冠総称)
  - 例: 「`type: code` のコード grader」(識別子付き) と「複数のグレーダーを組み合わせる」(無冠総称)
- **B. 一律統一** ── 全部 `grader` (英語) もしくは全部「グレーダー」(カタカナ) のどちらかに統一する。シンプルだが識別子との視覚的繋がりが弱まる

**修正パターン**:

- 記事冒頭で方針を 1 文明示する: 「`<name>` 付き修飾は英語表記、無冠の総称はカタカナで統一する」
- ヒット箇所すべてで方針との一致を確認、不一致箇所を Edit
- **修正後、再度 grep で残存を確認** ── 複数箇所に分散していることが多い

**本セッションの実例**:

記事内で `behavior` グレーダー、`program` グレーダー (カタカナ) と `code` grader、`prompt` grader、`trigger` grader (英語) が方針なく混在していた。ユーザーから「グレーダーをカタカナで表記するのか英語表記するのかの基準を教えて」と指摘され、方針 A (識別子付き=英語、無冠=カタカナ) で統一した。
