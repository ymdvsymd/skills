# Tech Blog from Docs

技術ドキュメント（複数ファイル・ディレクトリ・URL）を素材として、日本語の技術ブログ記事を生成するスキル。

このスキルの中核は **「生成後にユーザーが指摘するであろう問題を、生成前/生成後の自己フェーズで先回りで潰す」** 設計にある。単に何か書くだけのスキルではなく、ライターと編集者の両方を 1 つのワークフローに組み込んでいる。

## When to Use

- 社内勉強会（テクノ場、Lightning Talk など）の発表資料を、スライドではなくブログ記事として書きたい
- OSS や新しいツールを社内に紹介する技術記事を書きたい
- 長めの技術解説記事（15〜45 分の読み物）を作りたい
- 既存の英語ドキュメントを素材に日本語の解説記事を起こしたい
- 「why → what → how」の構造で技術概念を整理した記事を作りたい

このスキルを**使わない**ケース:

- 短いお知らせ・リリースノート程度の文章（このスキルの工程はオーバースペック）
- スライド形式の発表資料（このスキルはあくまでブログ記事用）
- API リファレンス・チュートリアルの 1 ステップなど、機械的に書ける文書
- 既に下書きがあり、推敲だけしたい場合（別途、推敲依頼として扱う）

## 引数

スキル発動時に以下が必要。揃っていない場合は最初に確認する：

| 引数 | 形式 | 例 |
|---|---|---|
| ソース | ディレクトリパス / ファイルパス（複数可）/ URL（複数可）の組み合わせ | `/path/to/docs/`, `[file1.md, file2.md]`, `<URL>` |
| 出力先 | 絶対パス。日付プレフィックスを付けたファイル名まで含む or ディレクトリ | `/path/to/output/2026-05-22-topic.md` or `/path/to/.history/` |

## Workflow

以下の 6 phase を順に実行する。各 phase の詳細はリンク先の reference を読むこと。

### Phase 1: Intent Capture（事前確認）

記事を 1 文字も書かないうちに、4 つの軸を確定させる。**Auto mode でも、この phase の確認は省略しない**（読者層を読み違えると全体の調子が崩れて、結局書き直しになるため）。

確認すべき 4 軸：
1. **対象読者の前提知識** — 専門用語の説明深さを決定する
2. **社内/組織文脈の織り込み度合い** — 一般化された技術記事か、現場固有の補強付きか
3. **記事のトーン** — 実利重視（コード中心）/ 概念重視（思想・設計判断中心）/ バランス型
4. **出力先と読了時間目安** — ファイルパスと、想定読了分数（デフォルト 30 分）

詳しい質問テンプレと選択肢の文言は [references/prep-and-structure.md](references/prep-and-structure.md) の Phase 1 セクションを読む。

### Phase 2: Source Research（素材調査）

ソースの種類と規模を判定し、調査戦略を決める。

- **小規模**（5 ファイル以下、ページ数十程度）→ 直接 Read で全読
- **中規模**（5〜20 ファイル）→ Read + Bash (`grep`, `head`) で骨子把握 + 必要箇所 Read
- **大規模**（20 ファイル以上、ドキュメント全体）→ **Explore subagent を 2〜4 並列** で観点別に分担

並列 Explore の観点割り（大規模時のテンプレ）:
- 観点 A: 概念・メンタルモデル（concepts, overview, getting-started）
- 観点 B: 使い方・ハウツー（consumer, producer, how-to）
- 観点 C: 運用・ガバナンス・統合（enterprise, integrations, CI/CD）
- 観点 D: リファレンス・補足（reference, troubleshooting）

各 subagent には「2,000〜3,000 字以内で報告、コード例・YAML 例を引用形で含めること」と明示する。

詳しい指示テンプレは [references/prep-and-structure.md](references/prep-and-structure.md) の Phase 2 セクションを読む。

### Example — Phase 3: Article Structure（記事構成）

**why → what → how の 3 部構成** で固定。これは技術記事として最も汎用性が高い構造で、本スキルはこのテンプレに沿って書く：

```
# タイトル
> リード（想定読了時間、対象読者）

## はじめに
(現状の痛みを描写、本記事の主張を 1 段落で予告)

## Why — なぜ X が必要なのか
### 1. 痛みポイント A
### 2. 痛みポイント B
### 3. 痛みポイント C
### 4. 痛みポイント D（必要なら）
### 補足: X 自身が掲げる "○つの約束"（あれば）

## What — X とは何か
### 1. 一行で言うと
### 2. メンタルモデル
### 3. プリミティブ / 構成要素
### 4. ライフサイクル / 動作の流れ
### 5. X ではないもの（混同しがちな概念）

## How — 具体的にどう使うか
### Phase 0: インストール / セットアップ
### ユースケース ①: ...
### ユースケース ②: ...
### ...
### ユースケース ⑤〜⑦: 重要ケースを網羅

## まとめ
(主張の再掲、明日試すコマンド数行)

## 参考リンク
```

各セクションの詳しい中身ガイドは [references/prep-and-structure.md](references/prep-and-structure.md) の Phase 3 セクションを読む。

### Phase 4: Writing（執筆）

[references/japanese-writing.md](references/japanese-writing.md) のライティングルールに従って書く。**ここで守るべき主な原則** は：

- **ルー語禁止**: 英動詞をサ変動詞化しない（NG: 「gate される」「scan する」「pin する」/ OK: 「ゲートにかける」「スキャンする/検査する」「固定する」）
- **固有名詞・術語は英語表記のまま OK**: `apm.yml`, `lockfile`, `manifest`, `primitive`, `harness`, `frontmatter` などの術語的英単語は地のままで良い
- **箇条書きの文末スタイル統一**: 1 つの箇条書きグループ内で「~こと」「~する」「名詞句」を混ぜない
- **コードブロックは fenced + 言語指定** （` ```yaml `, ` ```bash `, ` ```text ` など。markdownlint MD040 対策）
- **図は Mermaid で書く**（` ```mermaid ` ブロック）。**改行は `<br>` で行う**（ノードラベル内の `\n` ではなく `<br>` を使う ── Mermaid の仕様）
- **表は Markdown table**（罫線文字で表を書かない）

### Phase 5: Self-Review（自己レビュー）★ 最重要

書き終えた直後に、[references/self-review.md](references/self-review.md) のチェックリストを **全項目** 通す。違反を見つけたら、出力前に修正する。このフェーズの目的は **「ユーザーが指摘する前に自分で潰すこと」**。

本フェーズは内部で **2 段階** に分かれる:

#### Phase 5a: Self-Review (文体・構造)

文体・構造の品質チェック。次の 14 項目を順に通す:

1. 専門用語の前振り欠如 (JSON フィールド名・CLI フラグも対象)
2. 仕組み説明の曖昧さ (「自動で X する」「heuristic に〜」だけで終わっていないか)
3. 図の解釈の二義性 (ファイル構造と組織/クラウド構造の混同など)
4. 節内の重複・冗長性
5. ルー語 (英動詞サ変化 + 英単語 + 化された / ベース / 的 / -like / に + 動詞、英単語の地のまま使用)
6. 文末スタイルの不統一
7. サンプル名の整合性 (組織名・パッケージ名が記事全体で一貫しているか)
8. 文字数と読了時間目安の整合
10. 名詞-動詞の意味的整合 (目視) ── "Skill 工程に揃う" 等の不整合
11. 比喩・訳語の適切性 (目視) ── "録画" "隣を探索" "偽 tool" 等の不適切な表現
12. 主体/客体・関係性の明示 (目視) ── テスト入力か対象か、入力か出力かが明確か
13. 分類スキーマの明示 (目視) ── ラベル付け (個人/チーム/組織 等) の種類と基準
14. 折衷案で問題を覆い隠していないか (目視) ── ジレンマを中庸案で誤魔化していないか
15. 表記揺れ (カタカナ vs 英語) ── 「グレーダー」vs「grader」のような同一概念の混在を grep で検出

#### Phase 5b: Fact Check (事実整合性) ★ 新規

ハルシネーション検出 (項目 9):

- 記事中の具体的な事実主張 (CLI コマンド・フラグ・数値・YAML フィールド・JSON 出力例・運用 tips) を抽出
- 各々がソース doc に grep で確認できるか検証
- **subagent の研究結果はソースではない** ── 必ず一次ソース (元の md ファイル) で再確認
- 「妥当」「現実的」「推奨」「ベスト」と書いた主観 tips がソース doc の設計意図と矛盾しないか追加確認

各項目について、具体的な検出方法と修正パターンは [references/self-review.md](references/self-review.md) に書いてある。**機械的にチェックして直すこと**。「だいたい大丈夫そう」で出力しない。

修正したら **必ず全文を再 grep して同パターン残存が無いか確認する** ── 1 箇所だけ直して終わりにしない。

### Phase 6: Output

出力ファイルを書き出す（Write tool）。書き出した後、ユーザーへの 1 メッセージで以下を報告：

- 出力ファイルパス
- 文字数と推定読了時間（600 字/分換算）
- 記事の章構成（章タイトルの箇条書き）
- 設計判断のうち、ユーザーが後で議論するかもしれないポイント（例: 「ユースケース節は 6 個にしたが、削れるなら短くできる」）

## アンチパターン (Troubleshooting)

このスキルで **やってはいけない** こと：

- **Phase 1 を飛ばす** — 読者層が違うと全体の調子が崩れる
- **Phase 5 を飛ばす / 形式的に通す** — このスキルの存在意義の半分はここにある
- **Phase 5b (Fact Check) を skip する** — 嘘を書いて出すのは技術記事として致命傷。本セッションでは Phase 5b がなかったために `waza dev --model`、`--format detailed`、"post-merge が妥当" 等のハルシネーションがユーザー指摘まで残った
- **subagent の研究結果をそのまま記事に反映する** — subagent はハルシネーションする可能性がある。Phase 5b で必ず一次ソース (引数で渡された md ファイル) を grep で再確認する
- **ソース doc の設計意図と矛盾する運用 tips を書く** — 「妥当」「現実的」「推奨」「ベスト」と書いたものは、ソース doc の design / PRD と整合するか確認する
- **個別箇所の修正で全文 grep を忘れる** — ルー語や表記揺れは複数箇所に分散していることが多い。1 箇所修正したら必ず全文を再 grep
- **箇条書きや表の中で文末を混ぜる** — 機械的にチェックして直す
- **「読みやすくしました」「分かりやすく書きました」のような自己評価をユーザーへの最終報告に入れる** — 内容で勝負する
- **AskUserQuestion を Phase 1 以外で乱発する** — Phase 2〜6 は基本的に自走する。本当に判断つかない場合のみ確認
